Architecture Principles

01
Tool Composability
Individual tools are self-contained, discoverable packages that combine into complex workflows.
02
Sandboxed Execution
All agent execution runs in isolated Kubernetes containers with security policies.
03
Event-Driven Coordination
Components communicate through events, webhooks, and streaming protocols.
04
Durable State
Execution state persists across failures through checkpointing and replay.
05
Multi-Channel Delivery
Results delivered through Slack, API, and web interfaces based on context.

Enumerated System Flows

Seven core procedures that define how Centaur routes requests, isolates secrets, recovers from failure, and delivers results.

Flow 1: Agent Execution (Primary Request Path)

sequenceDiagram participant C as Client (Slack/API) participant API as centaur-api participant DB as PostgreSQL participant K8s as Kubernetes participant SB as Sandbox Pod C->>API: 1. POST /agent/execute API->>DB: 2. INSERT session (queued) API->>K8s: 3. Create pod (Job) K8s->>SB: 4. Start container + tools SB->>API: 5. POST /agent/ready API->>DB: 6. UPDATE running + checkpoint API-->>C: 7. SSE stream opened loop Reasoning Loop SB->>API: 8. SSE: thinking/tool_call API->>DB: 9. UPSERT checkpoint API-->>C: 10. Forward event end SB->>API: 11. SSE: done API->>DB: 12. UPDATE complete API-->>C: 13. SSE: complete, close API->>K8s: 14. DELETE pod
  1. Client sends POST /agent/execute with message, optional workflow context, and tool constraints.
  2. centaur-api writes an agent_session row to PostgreSQL (status: queued), allocating a session UUID.
  3. API creates a Kubernetes Job with the agent sandbox image, mounting tool volumes and injecting secrets via Iron-Proxy sidecar.
  4. K8s schedules the pod; the container starts, loads tool manifests, and connects back to the API via WebSocket.
  5. Sandbox sends a /agent/ready handshake confirming tool availability and resource allocation.
  6. API marks the session running, writes the initial checkpoint, and opens an SSE stream back to the client.
  7. Client receives event: started — the stream is now live.
  8. Agent loop executes: LLM call → tool selection → tool execution → observation. Each step emits an SSE event.
  9. After each step, the API upserts a checkpoint row so the session can resume from failure.
  10. Every SSE event is forwarded to the client in real-time (Slack message streaming or API response stream).
  11. On completion, the sandbox emits event: done with the final output.
  12. API writes final results to PostgreSQL (session complete, output stored).
  13. API sends event: complete and closes the SSE stream.
  14. API deletes the Kubernetes pod — no agent state leaks between sessions.

Flow 2: Slack Integration (User Interaction Path)

sequenceDiagram participant U as Slack User participant SW as Slack Webhook participant SB as slackbot (Hono) participant API as centaur-api U->>SW: 1. @centaur message SW->>SB: 2. POST /events (signed) SB->>SB: 3. Verify + deduplicate SB->>SB: 4. Normalize → agent request SB->>API: 5. POST /agent/execute SB->>SW: 6. chat.postMessage ("thinking…") SB->>SB: 7. Consume SSE, throttle SB->>SW: 8. chat.update (streaming) SB->>SW: 9. chat.update (final + attachments) SB->>SB: 10. Background poll SB->>U: 11. DM or thread reply
  1. User sends @centaur <message> in a Slack channel where the bot is installed.
  2. Slack POSTs a signed event to the registered webhook URL (/api/slack/events).
  3. slackbot verifies the HMAC signature against SLACK_SIGNING_SECRET and checks event_id for duplicates.
  4. The Slack event is normalized: channel context, thread parent, user identity, and message text are extracted into a standard agent request envelope.
  5. slackbot forwards to centaur-api via POST /agent/execute, receiving a stream endpoint in response.
  6. An initial Slack message is posted showing "thinking…" with the agent session ID as metadata.
  7. The Slackbot consumes the SSE stream, buffering text updates and respecting Slack's rate limits (1 update/sec).
  8. Incremental text is pushed via chat.update — the user sees the agent's response build in real-time.
  9. On stream completion, a final chat.update posts the complete response with attachments.
  10. A background poll monitors session status for late-arriving results or error states.
  11. If follow-up needed, the Slackbot DMs the user or posts in-thread.

Flow 3: Workflow Orchestration (Checkpoint-Replay)

sequenceDiagram participant T as Trigger participant API as centaur-api participant DB as PostgreSQL participant WP as Workflow Pod participant Ext as External APIs T->>API: 1. Trigger event API->>DB: 2. INSERT workflow_run API->>K8s: 3. Spawn pod WP->>DB: 4. LOAD last checkpoint loop Steps WP->>Ext: 5. Execute step Ext-->>WP: Result WP->>DB: 6. SAVE checkpoint end Note over WP: 7. Suspend capability Note over WP: 8. Resume from checkpoint WP->>DB: 9. Mark complete
  1. A trigger fires — Slack message matching a workflow pattern, webhook from an external system, or cron schedule.
  2. API inserts a workflow_run row (status: pending) with the workflow definition and trigger context.
  3. API spawns a Kubernetes pod with the workflow engine and serialized workflow DAG.
  4. On startup, the workflow engine queries PostgreSQL for the last checkpoint — if resuming, it picks up mid-graph.
  5. Each step executes: the pod calls the designated tool or external API, waits for the result.
  6. After each step, a checkpoint is saved: (step_id, input_state, output_state, timestamp) — this is the recovery boundary.
  7. Suspend: for long-running workflows (hours), the pod can be terminated and recreated later. State persists in PostgreSQL.
  8. Resume: a new pod loads the latest checkpoint and continues from the next uncompleted step.
  9. On completion, the pod marks the workflow_run as complete or failed.

Flow 4: Tool Execution Security (Secret Isolation)

sequenceDiagram participant A as Agent (sandbox) participant TS as Tool Server participant IP as Iron-Proxy (sidecar) participant Ext as External API A->>TS: 1. Tool invocation TS->>TS: 2. Build request TS->>TS: 3. Inject placeholder TS->>IP: 4. Forward with placeholders IP->>IP: 5. Resolve → real secrets IP->>IP: 6. Inject credentials IP->>Ext: 7. Authenticated request Ext-->>IP: 8. Response IP->>IP: 9. Filter sensitive headers IP-->>TS: 10. Sanitized response TS-->>A: 11. Tool result (JSON)
  1. The agent calls a tool: tool name + serialized arguments.
  2. The tool server resolves the handler from the registry and builds the outgoing HTTP request.
  3. Instead of real credentials, the request body contains placeholders: ${SECRET:ALCHEMY_API_KEY}.
  4. The tool server forwards this placeholder-laden request to the Iron-Proxy sidecar (localhost, same pod).
  5. Iron-Proxy resolves each placeholder against its secret store (injected at pod startup from Vault or K8s secrets).
  6. Real credentials are substituted: headers get Authorization: Bearer sk-live-..., query params get API keys.
  7. Iron-Proxy makes the actual outbound HTTP call to the external API.
  8. The external API returns a response — potentially including rate-limit headers, auth tokens in headers, etc.
  9. Iron-Proxy strips sensitive response headers (cookies, auth tokens, internal routing info) before passing back.
  10. The sanitized response is returned to the tool server.
  11. The tool server parses the response into the tool's output schema and returns it — the agent never sees a real secret.

Flow 5: Tool Development Lifecycle

flowchart LR A[1. Create
poetry init] --> B[2. Implement
Typer CLI + centaur-sdk] B --> C[3. Test
pytest + mock backends] C --> D[4. Register
auto-discovered by tool manager] D --> E[5. Deploy
container build + hot-reload] E --> F[6. Monitor

  1. Create: Scaffold a new Python package under tools/<category>/<tool-name>/ with pyproject.toml and centaur-sdk dependency.
  2. Implement: Write the tool as a Typer CLI application with Rich output. Use centaur-sdk.secret() for credentials — never hardcode secrets.
  3. Test: Unit tests with pytest using mock secret backends and fixture-based external API stubs.
  4. Register: Push to the monorepo; the tool manager auto-discovers via tools/*/pyproject.toml glob and registers it.
  5. Deploy: CI builds a container image; hot-reload in development, rolling update in production.
  6. Monitor: OpenTelemetry spans trace tool execution; errors surface in Sentry; usage metrics flow to Grafana.

Flow 6: Checkpoint-Replay Recovery

stateDiagram-v2 [*] --> Running Running --> Checkpointed: Save step N Checkpointed --> Running: Continue step N+1 Running --> Crashed: Pod dies / OOM / node eviction Crashed --> Recovering: New pod spawns Recovering --> Running: Load checkpoint, resume Running --> Complete: All steps done Complete --> [*]
  1. Agent or workflow executes normally — each step produces a checkpoint.
  2. A checkpoint is a PostgreSQL row: (session_id, step_number, full_state_blob, created_at). State includes LLM conversation, tool call stack, and context.
  3. If the pod crashes (OOM killed, node eviction, network partition), the session row remains in running status.
  4. The orchestrator detects the dead pod and spawns a replacement pod with the same session ID.
  5. On startup, the new pod loads the latest checkpoint: full conversation history, last completed step, pending tool calls.
  6. Execution resumes from step N+1 — the agent re-plays the last LLM call if needed, or picks up the next tool.
  7. The session continues until completion or another failure (cycle repeats).
  8. When all steps complete, final state is written and session marked complete.

Flow 7: Observability Pipeline

flowchart LR A[Agent Pod] -->|OTLP| B[Otel Collector] C[centaur-api] -->|OTLP| B D[slackbot] -->|OTLP| B B --> E[VictoriaMetrics] B --> F[Grafana] C -->|JSON logs| G[VictoriaLogs] A -->|JSON logs| G C -->|errors| H[Sentry] A -->|errors| H E --> F G --> F
  1. Every service (API, Slackbot, agent pods) is instrumented with OpenTelemetry SDKs — spans at service boundaries, tool calls, DB queries, and external APIs.
  2. Spans are exported via OTLP to a central OpenTelemetry Collector.
  3. The collector batches, filters, and routes: traces to VictoriaMetrics, logs to VictoriaLogs.
  4. Services emit structured JSON logs with PII redaction applied at the logging framework level.
  5. Error events are routed to Sentry with full stack traces and session context.
  6. Grafana dashboards consume VictoriaMetrics for request latency, tool execution counts, error rates, and sandbox resource usage.
  7. Custom business metrics (agent success rate, tool popularity, session duration) are emitted as DogStatsD counters.

Architecture Principles

01
Tool Composability
Self-contained, discoverable packages that combine into complex workflows.
02
Sandboxed Execution
Isolated Kubernetes containers with security policies — destroyed after each run.
03
Event-Driven
Components communicate through events, webhooks, and SSE streaming.
04
Durable State
Checkpoint-replay: execution survives pod crashes and node evictions.
05
Secret Isolation
Iron-Proxy sidecar: agents never see real credentials — only placeholders.

Enumerated System Flows

Seven procedures defining how Centaur routes requests, isolates secrets, recovers from failure, and delivers results.

Flow 1: Agent Execution (14 steps)

sequenceDiagram participant C as Client participant API as centaur-api participant DB as PostgreSQL participant K8s as Kubernetes participant SB as Sandbox C->>API: 1. POST /agent/execute API->>DB: 2. INSERT session (queued) API->>K8s: 3. Create pod K8s->>SB: 4. Start + mount tools SB->>API: 5. /agent/ready API->>DB: 6. UPDATE running API-->>C: 7. SSE stream open loop Agent Loop SB->>API: 8. SSE: thinking/tool_call API->>DB: 9. UPSERT checkpoint API-->>C: 10. Forward event end SB->>API: 11. SSE: done API->>DB: 12. UPDATE complete API-->>C: 13. SSE: complete, close API->>K8s: 14. DELETE pod
  1. Client sends POST /agent/execute with message, workflow context, tool constraints
  2. API writes agent_session row (status: queued), allocating session UUID
  3. API creates Kubernetes Job with sandbox image, tool volumes, Iron-Proxy sidecar
  4. K8s schedules pod; container loads tool manifests, connects via WebSocket
  5. Sandbox sends /agent/ready confirming tool availability and resources
  6. API marks session running, writes checkpoint, opens SSE stream
  7. Client receives event: started — stream is live
  8. Agent loop: LLM call → tool selection → tool execution → observation; each step emits SSE
  9. After each step API upserts checkpoint row for failure recovery
  10. Every SSE event forwarded to client in real-time
  11. Sandbox emits event: done with final output
  12. API writes final results to PostgreSQL
  13. API sends event: complete, closes SSE stream
  14. API deletes pod — no state leaks between sessions

Flow 2: Slack Integration (11 steps)

sequenceDiagram participant U as Slack User participant SW as Slack Webhook participant SB as slackbot (Hono) participant API as centaur-api U->>SW: 1. @centaur message SW->>SB: 2. POST /events (signed) SB->>SB: 3. Verify + deduplicate SB->>SB: 4. Normalize → request SB->>API: 5. POST /agent/execute SB->>SW: 6. chat.postMessage ("thinking…") SB->>SB: 7. Consume SSE, throttle SB->>SW: 8. chat.update (streaming) SB->>SW: 9. chat.update (final) SB->>SB: 10. Background poll SB->>U: 11. DM or thread reply
  1. User sends @centaur <message> in a Slack channel
  2. Slack POSTs signed event to /api/slack/events
  3. slackbot verifies HMAC signature against SLACK_SIGNING_SECRET, checks event_id for duplicates
  4. Event normalized: channel, thread, user, message extracted into standard envelope
  5. slackbot forwards to centaur-api via POST /agent/execute
  6. Initial message posted showing "thinking…" with session ID
  7. Slackbot consumes SSE stream, buffering and respecting rate limits (1 update/sec)
  8. Incremental text pushed via chat.update — user sees response build live
  9. On completion final chat.update posts complete response with attachments
  10. Background poll monitors for late-arriving results or errors
  11. If follow-up needed Slackbot DMs user or posts in-thread

Flow 3: Workflow Orchestration (9 steps)

sequenceDiagram participant T as Trigger participant API as centaur-api participant DB as PostgreSQL participant WP as Workflow Pod participant Ext as External APIs T->>API: 1. Trigger event API->>DB: 2. INSERT workflow_run API->>K8s: 3. Spawn pod WP->>DB: 4. LOAD last checkpoint loop Steps WP->>Ext: 5. Execute step Ext-->>WP: Result WP->>DB: 6. SAVE checkpoint end Note over WP: 7. Suspend — pod terminated Note over WP: 8. Resume — new pod loads checkpoint WP->>DB: 9. Mark complete
  1. Trigger fires — Slack pattern, webhook, or cron schedule
  2. API inserts workflow_run row (status: pending)
  3. API spawns K8s pod with workflow engine and serialized DAG
  4. On startup pod queries PostgreSQL for last checkpoint — if resuming, picks up mid-graph
  5. Each step: pod calls designated tool or external API, waits for result
  6. After each step checkpoint saved: (step_id, input_state, output_state, timestamp)
  7. Suspend: for long workflows (hours), pod can be terminated; state persists in PostgreSQL
  8. Resume: new pod loads latest checkpoint, continues from next uncompleted step
  9. On completion pod marks workflow_run as complete or failed

Flow 4: Tool Execution Security (11 steps)

sequenceDiagram participant A as Agent (sandbox) participant TS as Tool Server participant IP as Iron-Proxy participant Ext as External API A->>TS: 1. Tool invocation TS->>TS: 2. Build request TS->>TS: 3. Inject ${SECRET:KEY} TS->>IP: 4. Forward with placeholders IP->>IP: 5. Resolve → real secrets IP->>IP: 6. Inject credentials IP->>Ext: 7. Authenticated request Ext-->>IP: 8. Response IP->>IP: 9. Strip sensitive headers IP-->>TS: 10. Sanitized response TS-->>A: 11. Tool result (JSON)
  1. Agent calls tool with name + serialized arguments
  2. Tool server resolves handler from registry, builds HTTP request
  3. Credentials replaced with placeholders: ${SECRET:ALCHEMY_API_KEY}
  4. Tool server forwards placeholder-laden request to Iron-Proxy sidecar (localhost)
  5. Iron-Proxy resolves each placeholder against its secret store (Vault/K8s secrets)
  6. Real credentials substituted: headers get Authorization: Bearer sk-live-...
  7. Iron-Proxy makes actual outbound HTTP call to external API
  8. External API returns response — may contain rate-limit headers, auth tokens
  9. Iron-Proxy strips sensitive headers (cookies, tokens, routing info)
  10. Sanitized response returned to tool server
  11. Tool server parses into output schema — agent never sees a real secret

  2. Implement: Typer CLI + Rich output; use centaur-sdk.secret() for credentials
  3. Test: pytest with mock secret backends, fixture-based API stubs

Flow 6: Checkpoint-Replay Recovery (8 steps)

stateDiagram-v2 [*] --> Running Running --> Checkpointed: Save step N Checkpointed --> Running: Continue N+1 Running --> Crashed: Pod dies/OOM Crashed --> Recovering: New pod spawns Recovering --> Running: Load checkpoint, resume Running --> Complete: All steps done Complete --> [*]
  1. Agent executes normally — each step produces a checkpoint
  2. Checkpoint is PostgreSQL row: (session_id, step_number, state_blob, timestamp)
  3. If pod crashes (OOM, eviction, network), session stays running
  4. Orchestrator detects dead pod, spawns replacement with same session ID
  5. New pod loads latest checkpoint: full conversation, last step, pending calls
  6. Execution resumes from step N+1 — replays last LLM call or picks up next tool
  7. Session continues until completion or another failure (cycle repeats)
  8. On completion final state written, session marked complete

Flow 7: Observability Pipeline (7 steps)

flowchart LR A[Agent Pod]-->|OTLP|B[Otel Collector] C[centaur-api]-->|OTLP|B D[slackbot]-->|OTLP|B B-->E[VictoriaMetrics] B-->F[Grafana] C-->|JSON logs|G[VictoriaLogs] A-->|JSON logs|G C-->|errors|H[Sentry] E-->F;G-->F
  1. Every service instrumented with OpenTelemetry SDKs — spans at all boundaries
  2. Spans exported via OTLP to central collector
  3. Collector batches, filters, routes: traces → VictoriaMetrics, logs → VictoriaLogs
  4. Structured JSON logs emitted with PII redaction at framework level
  5. Errors routed to Sentry with full stack traces and session context
  6. Grafana dashboards consume VictoriaMetrics for latency, tool counts, error rates
  7. Custom metrics (success rate, tool popularity, session duration) via DogStatsD
